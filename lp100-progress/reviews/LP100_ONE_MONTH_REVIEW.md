## 1. 採用する評価方法（初期記録ベース）

チャレンジ初期の記録を確認すると、Day001から少なくともDay007までは、以下の同一フォーマットで日次記録が継続している。

1. 今日の成果
2. 作業時間
3. 詰まり（1つ）
4. 学び（1行）
5. 良かったこと（1つ）
6. 次回やること

これは実質的に、初期に定めた評価フレームとして扱える。  
よって本レビューでも、この6項目を週次粒度へ拡張して採用する。

週次評価では、次の形に読み替える。

1. 期間の成果
2. 投入量と進め方
3. 主要な詰まり
4. 問題への対処
5. 得た学び・使えるようになったツール
6. 次週へつながる到達点

## 3. 週次評価

## Week 1（Day001-007）

### 期間の成果
- Day001〜Day004で、HTML/CSSの基礎理解を進めながら、既存LPの骨子を使った差し替え制作を継続。
- Day005で、D2C向けのテンプレートを新設。
- Day006〜Day007で、物販テンプレをSaaSや別商材へ差し替え、AI差分運用の初期形を確立。

### 投入量と進め方
- 作業時間は長めだが、毎日「前日の振り返り → 差し替え → 微修正」の反復で進めている。
- 初期は手作業比率が高かったが、Day006から ChatGPT と Copilot の役割分担が入り、明確に生産性が改善した。

### 主要な詰まり
- CSSの基本理解不足（position、疑似要素、後勝ちルール、背景画像の扱い）。
- 手作業の文言差し替えに時間がかかり、インデント崩れや置換漏れが起きやすい。
- テンプレートを変えすぎると理解が追いつかず、構造理解に時間を要する。

### 問題への対処
- 検証ツールだけでなく、コードを読んで構造理解する姿勢へ切り替えた。
- ChatGPTでコピーを作り、Copilotで差分置換する流れを導入。
- Day007では「変えない判断」を行い、テンプレ検証を優先した。

### 得た学び・使えるようになったツール
- ChatGPT: コピー生成、構成相談
- GitHub Copilot: 差分置換
- Adobe Express: Hero画像の準備
- 基礎CSS: `position`, `:root`, `::before`, `::after`, `background-image`

### 次週へつながる到達点
- 「静的LPを1本作る」から、「テンプレを転用して別業種へ展開する」段階へ移行。
- AIを使って作業時間を圧縮する最初の成功体験ができた。

### Week 1評価
- 基礎構築としては十分に前進。
- 課題は多いが、問題の多くが「未理解」ではなく「どこを見れば直せるか」に変わり始めている。

## Week 2（Day008-014）

### 期間の成果
- 差分管理、Git復旧、CSSの可読性改善など、制作の再現性が上がった。
- Day013でCodex CLIを実運用し、AIへの再指示・却下・再提案という実務的な使い方に進化。

### 投入量と進め方
- 単純な差し替えより、方針の切り替えと作業手順の整備に時間を使っている。

- HTML用・CSS用で指示を分け、壊れやすい変更を分割した。
- Codexを「正解を出す機械」ではなく、再指示前提の実装担当として扱う方針が固まった。

### 得た学び・使えるようになったツール

- Codex CLI / VS Codeサイドバー

### 次週へつながる到達点
- AIの役割分担がかなり整理された。
- テンプレ量産より、「案件ごとに全体を最適化する」制作思想へ進んだ。

### Week 2評価
- この週は制作技術そのものより、「作り方」の質が大きく改善した週。

## Week 3（Day015-021）

### 期間の成果
- WordPress固定ページ実装、検証環境構築、確認用URLの共有、納品方式の再設計まで進んだ。
- Day016で ConoHa 上に検証用WordPressを構築し、実務フローをオンラインで再現。
- Day018〜Day020で画像運用、404解消、表示差分吸収、最終品質確認の手順を確立。
- Day021で、権限差を踏まえて「追加CSSなし」「`<style>`同梱」方式へ納品方法を再設計。

### 投入量と進め方
- 実装だけでなく、環境構築、クライアント想定の条件確認、納品方式の選択に時間を使っている。
- 「ローカル正本」「WordPressは検証/反映先」という役割分担が明確になった。

### 主要な詰まり
- 個人ブログ環境（JINテーマ）が検証に不向きで、ノイズが多い。
- WordPressで相対パス画像やSVGがそのまま使えない。
- テーマ由来の幅制限やフォント差で、ローカルと表示がズレる。
- 編集者権限では追加CSSが使えず、Day020の方式をそのまま流用できない。

### 問題への対処
- 検証専用WordPressを別で立てた。
- 画像をWebPに統一し、メディアURLへ差し替え、DevToolsで404を検証。
- `page-id` 限定CSSでテーマ干渉を局所的に打ち消した。
- 追加CSSが使えない前提で、カスタムHTMLブロック内に`<style>`を同梱する方式へ切り替えた。

### 得た学び・使えるようになったツール
- ConoHa WING / WordPress固定ページ運用
- Simple Custom CSS & JS
- DevTools Networkでの404調査
- PhotoshopによるWebP変換
- シェルスクリプトによるWordPress貼り付け用ファイル生成

### 次週へつながる到達点
- 「静的ファイルを作る人」から、「クライアントの環境制約に合わせて納品方式を変える人」へ進化。
- 実務の本質が、実装力だけでなく環境適応力だと理解できている。

### Week 3評価
- 1か月の中でも最も実務力が伸びた週。
- LP制作だけでなく、公開前の検証・引き渡し・制約対応まで視野が広がった。

### 得た学び・使えるようになったツール

- 納品チェックリスト運用
- Telemetry設計

- Formspree

### 投入量と進め方
- フロントエンド実装力の拡張と、公開運用の現実的な制約対応が同時進行。
- 「理想構成を目指す」より、「公開を成立させる最小構成へ切り替える」判断が増えている。

### 主要な詰まり
- WordPress上でカスタムJS保存が `Forbidden access` に阻まれる。
- `SiteGuard Lite` / WAF により、理想のJS運用が成立しない。
- FormSubmitは初回アクティベーション未完了だと、PDF遷移ではなく確認画面が出る。

### 問題への対処
- JSを分割し、保存ブロックの原因を切り分けた。
- それでもブロックされると判断した時点で、「JSなし公開優先」へ方針転換した。
- FAQを常時表示化、PDFフォームを通常POST化、必要ならPDF直リンクへ切り替える、というフォールバックを設計した。
- 計測・UTM・詳細イベントは第2フェーズへ分離し、初回公開の成立を優先した。

### 得た学び・使えるようになったツール
- Lighthouseを使った品質改善
- React + TypeScript + Tailwind + Vite
- `window.LP_CONFIG` による運用設定の一元管理
- GA4 / Meta Pixel の導入設計
- TimeRex / FormSubmit の実運用前提検証
- ConoHa onboarding案内資料の整備

### 次週へつながる到達点
- 高機能実装だけでなく、インフラ制約下で「公開を止めない代替案」を出せるようになった。
- フロントエンドの技術幅は大きく広がり、今後は「標準運用の固定」が主課題になった。

## 4. 1か月で何ができるようになったか

## 技術面
- 静的HTML/CSS/JSで、複数業種のLPを短期間で組める
- レスポンシブ、a11y、Lighthouse改善を前提に品質を見られる
- React + TypeScript + Tailwind でもLPを構築できる
- 画像最適化（WebP、命名統一、参照戦略）を運用に落とせる
- フォーム、PDF導線、GA4、Meta、UTMの実装設計ができる

## 実務面
- クライアント想定のヒアリング、要件定義、進行管理ができる
- WordPress固定ページへの反映方式を、権限やテーマ差に応じて選べる
- 確認用URL、パスワード保護、納品ZIP、再送、検収までの流れを回せる
- 制約が強い環境で、代替案を含めて前進できる

## AI運用面
- ChatGPT: 要件整理、コピー、方針決定
- Copilot: 差分適用
- Codex: 実装担当としての差分生成、レビュー前提運用
- Claude系: 依頼文整理、運用ドキュメント補助
- 生成AI画像: 画像制作と実装フローの検証

## 5. 現時点の主要課題

1. WordPress上の標準公開パターンがまだ固定し切れていない。
2. JSあり運用がWAFやセキュリティ設定に阻まれるケースの正式手順が未確立。
3. 計測実装は入れられるが、公開後に確実に動作検証する標準QAがまだ弱い。
4. CSS差分運用は改善したが、長期保守時の整理ルールはさらに強化余地がある。
5. 外部サービス（FormSubmit, TimeRex, GA4, Meta）の本番アクティベーションを含む運用手順が、環境依存で止まりやすい。

## 6. 次の1週間で優先すべきこと

1. WordPress納品の標準を3パターンに固定する
   - 静的ZIP納品
   - WordPress no-JS公開
   - WordPress JSあり公開（条件付き）

2. 公開前QAチェックリストを固定する
   - CTA遷移
   - フォーム送信
   - PDF導線
   - 法務ページ
   - 404
   - GA4/Meta
   - SP/PC表示

3. 外部サービスの「初回有効化」手順をテンプレ化する
   - FormSubmitアクティベーション
   - GA4確認
   - Meta Pixel確認
   - TimeRex遷移確認

4. 実案件向けの標準ドキュメントを固定する
   - 要件確認シート
   - 納品メモ
   - 公開後の更新手順
   - ブロッカー発生時の代替案テンプレ

## 7. 最終所見

この1か月での最大の進歩は、  
「LPを作れるようになったこと」そのものではなく、  
「環境制約・権限差・公開条件・クライアント都合を含めて、成立する形へ着地させる力」がついたことにある。

初期は、HTML/CSSの理解と差し替え速度が課題だった。  
現在は、そこを超えて、

- どの実装方式を選ぶか
- どこまでを初回公開に含めるか
- 何を第2フェーズへ切り出すか
- どの手順をテンプレ化すべきか

まで考えて動けている。

したがって、Day036時点の評価は  
「制作練習フェーズを抜け、実務化フェーズに入った」  
と判断する。

今後の伸びしろは、制作力そのものよりも、  
「標準化された公開運用」「環境差に強い納品パターン」「計測の検証精度」の3点に集中している。
