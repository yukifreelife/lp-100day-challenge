# Day045 - 次回案件の標準プロセス案

## 目的
- 今回の案件で出た
  - 受注時のスコープ過多
  - WordPress運用方式の後出し確定
  - 仮設定の本番残置
  - 計測レビュー証跡不足
  - ドキュメント複製ドリフト
  を次回以降で防ぐ。

## 基本方針
- `公開方式を先に決める`
- `価格と境界を先に切る`
- `本番運用責任を先に固定する`
- `レビュー証跡を残す`
- `正本ファイルを減らす`

## 標準プロセス

### 1. 相談・受注前ヒアリング
- 目的:
  何を作る案件かではなく、どこまでを請ける案件かを先に定義する。
- 必須確認:
  - 主要CV
  - 副次CV
  - `流入 -> LP -> 予約 -> 面談 -> 申込` の全体ファネル
  - 現状の歩留まり
  - 断り理由
  - 期限
  - 予算
  - 納品形態
  - クライアントの更新能力
  - 使用する予約導線
  - リード取得方式
  - 計測要件
- 成果物:
  - `PROJECT_INTAKE_CHECKLIST.md`
  - `REQUIREMENTS_CONFIRMED.md`
  - `FUNNEL_BOTTLENECK_MAP.md`
- ゲート:
  - `静的納品`
  - `WordPress納品`
  - `公開後レビュー`
  を分離して見積もること
  - LPが解く課題と、営業/商品設計側で解く課題を分けること

### 2. 公開方式チェック
- 目的:
  後から「このCMSでは想定どおり入らない」を防ぐ。
- 必須確認:
  - HTMLの入れ方
  - CSSの入れ方
  - JSの入れ方
  - フォームの実装方式
  - 予約導線の遷移方式
  - 計測タグの注入経路
- 成果物:
  - `DELIVERY_ARCHITECTURE_DECISION.md`
- ゲート:
  - ここが決まるまで「管理画面で簡単に直せます」と言わない

### 3. 見積・契約分離
- 標準の切り方:
  1. LP制作・初稿
  2. CMS移行 / 公開支援
  3. 公開直後の軽微修正
  4. 公開後計測整備
  5. 初回レビュー
  6. 継続改善伴走
- 原則:
  - `公開後レビュー` は初回制作に含めない
  - `WordPress納品` は静的LPの延長ではなく別 line item とする
  - `軽微修正` は回数または期間を契約上で固定する
- 成果物:
  - `ESTIMATE_SCOPE_MATRIX.md`
  - `CLIENT_PROPOSAL_SEND.md`

### 4. 制作フェーズ
- 目的:
  LP正本を、公開方式に合わせて作る。
- 実装前の追加確認:
  - 競合との差別化
  - トレーナー本人を選ぶ理由
  - 高単価でも納得される証拠
  - Instagram流入で期待される人物像との整合
- 実施内容:
  - 構成
  - 原稿
  - デザイン
  - 実装
  - 法務
  - 予約導線
  - PDF導線
- 原則:
  - 正本は `source/` か `current/` に一本化する
  - 日次ディレクトリはログ用途に限定する
- 成果物:
  - `index.html` / `styles.css` / `script.js`
  - `README.md`
  - `CLIENT_README.txt`
  - `VALUE_PROPOSITION_REVIEW.md`

### 5. 公開前チェック
- 目的:
  本番へ残してはいけない暫定設定をゼロにする。
- 必須チェック:
  - 予約URL
  - フォーム受信先
  - 自動返信文
  - PDFリンク
  - 法務リンク
  - GA4 ID
  - Meta Pixel ID
  - クライアント所有アカウントかどうか
  - 本番URL
  - 画像URL
- 特に禁止:
  - 仮メールアドレスのまま公開
  - 作業者アカウント依存のまま公開
  - 仮ドメイン / 仮URL残し
- 成果物:
  - `PRE_LAUNCH_CHECKLIST.md`
- ゲート:
  - 1つでも未確定があれば公開しない

### 6. 公開
- 目的:
  最小成立条件を満たした状態でリリースする。
- 最小成立条件:
  - 内容が読める
  - 予約できる
  - PDF導線が機能する
  - 法務リンクが開く
- 例外対応:
  - 技術ブロッカーがある場合は、`公開優先` の fallback を採用してよい
  - ただし fallback はクライアントに明示する
- 成果物:
  - `PUBLIC_RELEASE_EXECUTION_STEPS.md`
  - `CLIENT_PUBLIC_URL_SEND.md`

### 7. 公開直後の修正フェーズ
- 目的:
  公開阻害や視認性の問題だけを短期で収束させる。
- 区分:
  - Blocker
  - High
  - Medium
  - Low
- 原則:
  - ここでは `公開品質の確保` に集中する
  - 計測拡張や導線分析は後ろへ送る
- 成果物:
  - `CLIENT_FEEDBACK_TRACKER.md`
  - `FIX_PRIORITY_MATRIX.md`

### 8. 計測整備フェーズ
- 目的:
  予約までの離脱仮説を見られる最小計測を入れる。
- 最小計測の標準:
  - CTA総数
  - CTA位置別
  - 主要セクション到達
  - PDF入口別
  - PDFフォーム開始
  - PDFフォーム送信着手
  - UTM保持
- 注意:
  - LPイベントだけで最終予約完了を断定しない
  - 送信着手と送信完了は分けて扱う
- 成果物:
  - `MEASUREMENT_EXECUTION_PLAN.md`
  - `MEASUREMENT_VALIDATION_LOG.md`
  - `MEASUREMENT_SHARE_TEMPLATE.md`

### 9. レビューフェーズ
- 目的:
  実データで `数値の事実 / 仮説 / 次アクション` を返す。
- 必須証跡:
  - GA4スクリーンショットまたはエクスポート
  - FormSubmit件数メモ
  - TimeRex補助確認メモ
  - 外部流入要因メモ
- 可能なら追加で持つもの:
  - 予約完了数
  - 面談実施率
  - 申込率
  - 断り理由メモ
- 禁止:
  - 仮数値だけで納品扱いにする
  - サンプル文面を実績文面の代わりに使う
- 成果物:
  - `MEASUREMENT_OBSERVATION_LOG.md`
  - `CLIENT_MEASUREMENT_REVIEW_FINAL.md`
  - `REVIEW_EVIDENCE_ARCHIVE.md`
  - `IMPROVEMENT_PRIORITY_3LEVELS.md`

### 9.1 改善提案の返し方
- 原則:
  改善案は毎回1本ではなく、深さを分けて返す。
- 標準の3段階:
  1. `軽微修正`
  2. `訴求修正`
  3. `事業課題に踏み込む提案`
- 目的:
  - 無難なUI修正だけで終わらせない
  - クライアントが予算と深さを選べるようにする
- 成果物:
  - `IMPROVEMENT_OPTIONS_MATRIX.md`

### 10. 請求・クローズ
- 原則:
  - `初回制作`
  - `計測レビュー`
  は別請求とする
- クローズ条件:
  - 納品物共有
  - クライアント受領
  - 請求送付
  - 入金確認
  - 最終受領返信
- 成果物:
  - `CLIENT_INVOICE_SEND.md`
  - `CLIENT_PAYMENT_ACK_SEND.md`
  - `PROJECT_CLOSE_LOG.md`

### 11. 継続提案
- 原則:
  `継続も可能です` ではなく、継続時の判断材料を固定して提案する。
- 必須明文化:
  - 何を確認するか
  - どの頻度で見るか
  - どの指標で判断するか
  - どこまで対応するか
- 標準プラン例:
  1. 月次レビューのみ
  2. 月次レビュー + 改善提案
  3. 月次レビュー + 改善提案 + 実装
- 成果物:
  - `RETAINER_SCOPE_MATRIX.md`

## 標準で使うファイル構成
- `current/`
  - 現行正本
- `logs/`
  - 日次ログ
- `client/`
  - 送付文面
- `ops/`
  - 公開手順、反映手順、チェックリスト
- `analysis/`
  - 計測ログ、レビュー資料

## 標準運用ルール
- 正本は常に1つにする
- 日次ファイルは `何をしたか` だけを書く
- クライアント文面は `送ったもの` と `草案` を分ける
- 仮設定は `TEMP_` 明記し、公開前チェックで全削除する
- 作業時間は当日中に記録する
- `再構成メモ` は補助扱いにし、利益計算の一次ソースにしない

## 見積の標準基準

### 初回制作
- 含む:
  - 構成
  - 原稿支援
  - 実装
  - 法務
  - 主要導線
- 含まない:
  - CMS移行
  - 公開後レビュー
  - 詳細計測整備

### CMS移行 / 公開支援
- 含む:
  - 本番反映
  - 導線確認
  - 表示確認
- 含まない:
  - 詳細イベント設計
  - 継続改善

### 計測整備
- 含む:
  - 最小イベント設計
  - 実装
  - 確認
- 含まない:
  - 長期分析
  - 改善実装

### 初回レビュー
- 含む:
  - 一定期間の観測
  - 仮説整理
  - 次アクション提案
- 含まない:
  - 改善実装
  - 継続伴走

## 今回案件から残すもの
- 公開優先の判断基準
- 非エンジニア向け案内資料の作り方
- 計測共有テンプレ

## 今回案件からやめるもの
- 仮受信先のまま公開へ進めること
- 日別ディレクトリへ正本を複製し続けること
- `1案件に全部載せる` 受け方

## 次回案件の開始時に最初にやること
1. `PROJECT_INTAKE_CHECKLIST.md` を埋める
2. `DELIVERY_ARCHITECTURE_DECISION.md` で公開方式を確定する
3. `ESTIMATE_SCOPE_MATRIX.md` で line item を分ける
4. `PRE_LAUNCH_CHECKLIST.md` を先に作る
5. 正本フォルダを `current/` に固定する
