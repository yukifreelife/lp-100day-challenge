# 修正依頼受付チェックリスト
## 12 Revision Request Intake Checklist

**使う場面**: クライアントから修正依頼が来たとき、対応前に内容を切り分けるとき

## この場面の目的
- 修正依頼をそのまま受けず、`今回の範囲内か / 別対応か / 優先度は何か` を整理する。
- 追加工数や仕様崩れを防ぐ。

## 依頼内容の確認
- [ ] どのURL / どの版に対する指摘か確認した
- [ ] どの画面 / どの箇所の修正か特定した
- [ ] 何をどう変えたいかを具体化した
- [ ] 修正理由を確認した
- [ ] 期限を確認した
- [ ] 参考イメージやスクリーンショットを受領した

## 範囲判定
- [ ] 契約範囲内の軽微修正か判定した
- [ ] 構成変更か文言変更かデザイン変更か判定した
- [ ] 公開品質の不具合か改善要望か判定した
- [ ] 別フェーズ扱いが妥当なら、その理由を説明できる

## 優先度判定
- [ ] Blocker / High / Medium / Low を付けた
- [ ] 他箇所への影響を確認した
- [ ] 計測や導線に影響するか確認した
- [ ] 法務や表現リスクに影響するか確認した

## 追加対応時の確認
- [ ] 追加工数が発生するか判断した
- [ ] 追加見積が必要か判断した
- [ ] 追加対応は承認取得後に着手する前提を守る
- [ ] 承認者と承認方法を確認した
- [ ] 対応期限と返信期限を提示できる
- [ ] 対応しない場合の理由を整理した

## 完了条件
- [ ] `CLIENT_FEEDBACK_TRACKER.md` に記録した
- [ ] 範囲内 / 別対応 / 保留 の判定が明確
