# 初回相談・ヒアリング時チェックリスト
## 01 Intake And Hearing Checklist

**使う場面**: 初回相談、問い合わせ後の打ち合わせ、受注前ヒアリング

## この場面の目的
- `何を作るか` より先に、`どこまで請けるか` を定義する。
- LPで解ける課題と LP 外課題を分ける。

## 聞き漏らし防止チェック

### 基本条件
- [ ] 案件名 / 商材名 / 事業名を確認した
- [ ] 誰向けの案件か確認した
- [ ] 主CV を確認した
- [ ] 副CV を確認した
- [ ] 希望納期を確認した
- [ ] 予算上限を確認した
- [ ] 希望する納品形態を確認した

### 全体ファネル
- [ ] `流入 -> LP -> 予約 / 問い合わせ -> 面談 / 商談 -> 申込 / 契約` の流れを聞いた
- [ ] いま詰まっている場所をクライアント認識で聞いた
- [ ] 断られる理由や離脱理由を聞いた
- [ ] 面談後の流れを聞いた
- [ ] 契約率や面談実施率など、把握している数字 / 把握していない数字を分けた

### クライアントの期待
- [ ] LPに何を期待しているか聞いた
- [ ] デザイン改善と成果改善を同一視していないか確認した
- [ ] 公開後も見てほしい期待があるか聞いた
- [ ] 計測や数値確認も期待しているか聞いた
- [ ] クライアントが自分で直したい範囲を聞いた

### リスク発見
- [ ] LPだけでは解けなさそうな課題があるか洗った
- [ ] 予約オペレーションや商談設計がボトルネックになっていないか確認した
- [ ] 価格やオファーの出し方に迷いがないか確認した
- [ ] ステークホルダーが他にいるか確認した

### ステークホルダー分解
- [ ] 予算を最終的に決める人を確認した
- [ ] デザイン / 文章確認で口を出す人を確認した
- [ ] 技術判断や WordPress 事情に口を出す人を確認した
- [ ] 広告や集客方針を変える人を確認した
- [ ] 返信遅延や確認待ちの起点になる人を確認した
- [ ] その人たちがいつ登場するかを確認した

## この時点で止める条件
- [ ] 主CV が曖昧なまま
- [ ] 予算 / 納期 / 納品形態が曖昧なまま
- [ ] LP 外課題が大きいのに、LPだけで解決する前提になっている
